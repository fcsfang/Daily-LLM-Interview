## 1. 今日面试真题精讲

### 题目 1：你在 Agent 中如何设计长短期记忆？当新抽取的记忆与旧记忆发生冲突时，你是如何裁决的？（如用户更改了偏好）

**来源依据：**
- 字节跳动大模型实习面经：从Agent记忆到RAG优化，13道真题解析助你轻松拿下Offer！ - https://gitcode.csdn.net/6a2ccdca10ee7a33f27c07bf.html - 面经或社媒 - 需进一步验证。本文来源为面经，但内容是面试官对项目的深度追问，非常贴近实战。

**可信度：**
中（信息来源为面经搬运，但问题设计精妙，符合高级面试追问逻辑）

**考察点：**
Agent 记忆设计、结构化存储、冲突仲裁、工程鲁棒性。

**面试口头版回答：**
在我的项目中，我把记忆分成了短期和长期两层。短期记忆存最近几轮的原始对话，保证对话的连贯性；长期记忆则由模型在每轮对话后，通过一个轻量 prompt 抽取出结构化条目，比如“用户偏好”或“硬约束”。遇到冲突时，我不会简单粗暴地覆盖。我会采用“时间戳 + 来源置信度”仲裁。比如用户明确说“改成只看华东”，这是高置信度的新指令，我会将旧的“全国”条目标记失效。但如果只是模型推断的“可能喜欢”，而旧的“显式说喜欢”，我会两者都保留，并在检索时优先返回置信度高的。这样既不会丢失历史信息，也不会用过时的偏好答题。

**深入理解版回答：**
一个好的记忆系统是 Agent 的“长期大脑”。设计上，我遵循“提取-压缩-更新”三阶段。
1.  **提取**：每轮对话后，用一个专门的 prompt（或小模型）将对话中的关键信息抽取成结构化条目，字段包括：`类型`（偏好、约束、事实）、`内容`、`来源轮次`、`时间戳`、`置信度`（显式说=高，模型推断=中，对话上下文=低）。然后过滤掉寒暄等无长期价值的条目。
2.  **压缩**：长期记忆库会不断膨胀，所以需要摘要合并。定期对同类型、同主题的条目进行合并，保留“最新值 + 关键历史变更”，防止冗余。一些关键的硬约束（比如“预算上限”），我会单独标记，不参与摘要合并，避免被“平均”掉。
3.  **冲突更新**：这是面试中最容易挖深的地方。当新条目与旧条目信息矛盾（如用户改了口味），我设计了三级仲裁：
    *   **硬裁决**：如果新旧条目都来自用户**显式声明**，则以**时间戳最新**为准，旧条目标记为 `失效`，但不物理删除。
    *   **软仲裁**：如果新条目标记是“中等置信度”，旧条目标记是“高置信度”，则保留旧条目，并添加新条目，但设置其置信度为“低”。
    *   **检索时仲裁**：在检索时，会优先返回置信度高、且非“失效”状态的条目。这样既不丢信息，又能保证答案是当下最可靠的。

**常见追问与回答：**
- **追问**：记忆太多了，如何筛选进上下文？
    - **回答**：我不会全量塞入。我会将长期记忆条目向量化，根据当前 query 进行相关性召回，然后结合“时近性”做一个加权重排，通常只取最相关的 3-5 条。硬约束则放弃筛选，每轮都带。
- **追问**：这种“值不值得存”和“冲突仲裁”完全依赖 prompt 吗？
    - **回答**：我用规则+模型结合。规则先做粗筛（比如太短、纯寒暄直接丢）。语义判断（“是否值得存”、“是否真冲突”）则用一个小模型或调优过的 prompt。纯规则容易遗漏重要信息，纯模型成本高且不稳定，组合更优。

**项目联系：**
这个知识点直接对应了一个“带记忆的对话 Agent”项目的核心难点。在您的项目中，可以具体描述，比如：“我在做一个内部知识库问答 Agent，用户经常会说‘我只看华东区数据’，过了几轮又说‘加上华南区’。我的冲突仲裁机制就能处理这种偏好变更，避免它反复用旧限制回答。”

### 题目 2：Agent 的 Tool Calling 存在‘过度调用’或‘错误调用’的问题，你有什么工程经验来缓解这个问题？

**来源依据：**
- 大厂LLM应用岗上岸面经：面28家拿offer，拆解“必问考点+避坑指南” - https://juejin.cn/post/7531039727782068274 - 面经或社媒 - 需进一步验证。文中提到“Function Call用的是LangChain的Tool机制，遇到过‘调用工具频繁’的问题，后来加了‘反思步骤’”。
- 小林面试笔记 - https://xiaolinnote.com/ai - 技术博客 - 需进一步验证。该网站系统整理了Agent面试题，强调了工具调用的工程实践。

**可信度：**
中（集合了面经和博客的观点）

**考察点：**
Agent Tool Calling、Prompt 约束、反思机制、安全过滤。

**面试口头版回答**
这是个非常常见的工程痛点。我遇到过模型每句都去调工具，或者把“查天气”和“设提醒”混淆。我的做法有三层：第一，在 System Prompt 中明确工具的**调用条件和副作用**，比如“只有用户明确提到股票代码时，才调用查询股价工具”。第二，增加了 **Reflection（反思步骤）**，模型在决定调用前，先问自己一句“这个问题真的需要调用工具吗？是否已有足够信息？”第三，实现了一个**轻量级的预检查逻辑**，比如在调用“发送邮件”这类有副作用的工具前，用正则或其他规则检查收件人地址格式，不合法就不让模型调用。通过这三层，工具调用的误调用率显著降低。

**深入理解版回答：**
“工具滥用”是 Agent “幻觉”的一种表现，即模型误以为任务复杂到必须调用工具。工程上可以从**模型端**和**系统端**双管齐下。

1.  **模型端（Prompt 工程 + 反思）**：
    *   **精细化 Prompt**：在 tool description 里写清楚工具的功能、**限制**和**调用前提**。例如，给“search_news”工具的描述加上“仅用于查询最新新闻，不要用于检索用户个人信息”。
    *   **思考-行动-观察（ReAct）范式增强**：在 ReAct 循环中加入一个 `Think` 步骤，强制模型在 `Action` 之前先输出思考内容：“用户的问题是’今天天气怎么样’，这显然需要调用天气查询工具，而非我的内部知识库。” 这其实就是一种反思。
    *   **Few-Shot 示例**：在 prompt 中提供几个明确“不该调用”或“应该拒绝”的例子，比如“用户问’你好’时，直接回复，不调用任何工具”。

2.  **系统端（安全阀 + 后置校验）**：
    *   **预检查规则**：对于有副作用的工具（写数据库、发消息），在执行前增加规则校验。比如，调用“发送消息”工具时，检查接收者ID是否在模型允许的范围内；调用“创建订单”工具时，检查金额是否超限。
    *   **结果验证**：模型调用工具获得结果后，不直接输出。先让模型验证结果是否合理。比如，模型调用了“用户信息查询”工具，返回的年龄是 150 岁，这个结果明显不合理，应触发重试或纠错流程。
    *   **调用频率与限流**：如果一个 Agent 在单次回答中连续调用工具超过某个阈值（如 10 次），可能进入了死循环或逻辑混乱，应强制终止或回滚到上一步。

**常见追问与回答：**
- **追问**：如何确保模型调用工具时，传入的参数是正确的？
    - **回答**：这是结构化输出（Structured Output）的关键。我会使用框架（如 LangChain 的 `with_structured_output`）或通过 prompt 强制模型输出 JSON，并定义严格的 JSON Schema。对于日期、数字等有格式要求的参数，可以在后处理中对参数进行格式校验和修正。
- **追问**：你的“反思步骤”在代码层面是如何实现的？
    - **回答**：本质上是一次额外的模型调用。在 Agent 的主循环里，当模型决定要调用一个工具后，我先不执行，而是将模型的决定（工具名+参数）作为新的 prompt 输入给模型，要求其进行批判性思考：“确认一下，调用这个工具解决用户问题是最高效的吗？”。只有当反思结果也是肯定时，才真正执行工具。

**项目联系：**
您可以在项目中描述：“我开发了一个个人智能助理 Agent，它通过‘反思步骤’来减少不必要的 API 调用。例如，当用户问‘帮我看看我的日程’，模型不再先去查数据库，而是先反思‘用户的问题是否可以通过直接回答完成？信息是否存在于我的短期记忆中？’ 如果上轮聊天中用户刚说过下午有会，模型就会直接回答，而不是去调取数据库工具，大大降低了延迟和成本。”

**记忆关键词：**
#ToolCalling #反思机制 #Prompt约束 #参数校验 #结构化输出

### 题目 3：请对比 ReAct 和 Plan-and-Execute 两种 Agent 设计模式，在复杂任务和错误恢复上有何不同？

**来源依据：**
- 小林面试笔记 - https://xiaolinnote.com/ai - 技术博客 - 需进一步验证。该博客明确指出“重点是 ReAct、Plan-and-Execute、Reflection 这三种设计模式”。
- LLM & VLM & Agent 面试问题总结 - https://github.com/datawhalechina/hello-agents/blob/main/Extra-Chapter/Extra01-%E9%9D%A2%E8%AF%95%E9%97%AE%E9%A2%98%E6%80%BB%E7%BB%93.md - 面经或社媒 - 需进一步验证。文档中也提及了 Agent 的规划能力，如 CoT, ToT。

**可信度：**
中（综合了公开博客和 Git 文档的信息，是公认的核心考点）

**考察点：**
Agent 设计模式、任务分解、规划与执行、错误处理的工程策略。

**面试口头版回答：**
ReAct 模式像一个“边想边做”的人，它让模型在推理和行动间循环，适合在不确定的环境中灵活应变，比如需要从网页中逐步搜索信息。但它也容易陷入局部最优，逻辑不够长远的任务容易出错。而 Plan-and-Execute 模式就像“先规划再执行”，模型先制定一个清晰的步骤计划，再按顺序执行。这种方式任务分解更清晰，全局逻辑更好，但缺点是一旦第一步出错，后面就全错了。错误恢复上，ReAct 可以在失败的步骤后直接调整下一步行动，更灵活；而 Plan-and-Execute 则需要重新制定整个计划，成本更高。

**深入理解版回答：**
这两种模式的核心区别在于“规划”和“执行”是交织还是分离。

*   **ReAct (Reason + Act)**
    *   **工作流**：Thought -> Action -> Observation -> (Thought -> Action…) -> Final Answer。
    *   **优点**：
        1.  **灵活性极高**：模型可以观察到行动结果后，动态调整下一步，非常适合开放式、探索式的任务。
        2.  **错误恢复能力好**：单步失败不会导致整个任务崩溃，Agent 可以根据错误反馈（Observation）自动修正下一步 Action。
    *   **缺点**：
        1.  **Token 开销大**：每一步都需要生成 Thought，导致推理成本高、延迟高。
        2.  **易产生循环**：模型可能在几个 Action 间来回尝试，陷入死循环，需要设置最大轮数。

*   **Plan-and-Execute (Plan then Execute)**
    *   **工作流**：Plan (生成步骤列表) -> Execute Step1 -> Execute Step2 -> ... -> Final Answer。
    *   **优点**：
        1.  **任务分解清晰**：显式的计划让模型有能力处理需要长链条推理的复杂任务，比如“规划一次旅行”。
        2.  **高可观测性**：每一步都能独立记录、监控和 Debug，方便做任务调度和依赖管理。
    *   **缺点**：
        1.  **容错性差**：初始计划是基于模型预测的，如果环境变化或计划本身有漏洞，后续步骤会全部执行错误。
        2.  **不够灵活**：不能很好地处理执行过程中出现的意外情况。错误恢复通常需要“重新规划”整个步骤。

**工程实践总结**：在实际项目中，我会混合使用。一个复杂的任务，先用 Plan-and-Execute 制定宏观计划，但每个子步骤内部可以跑一个 ReAct 循环来处理细节。比如旅行计划 Agent，先规划“订机票->订酒店->查天气”，在“查天气”这一步，再跑一个 ReAct 来搜索天气、确认出行建议。

**常见追问与回答：**
- **追问**：你提到错误恢复，Plan-and-Execute 模式具体如何实现重新规划？
    - **回答**：通常有两种。一种是“简单重试”，重新跑一遍完整的 Plan 流程；另一种是“动态修正”，当步骤 2 失败时，将失败信息和当前状态（已完成步骤1）作为新上下文，让模型只重新生成步骤 3 及其之后的任务，这更高效。
- **追问**：如果一个任务需要多源数据交叉验证，哪种模式更合适？
    - **回答**：Plan-and-Execute 更合适。因为它可以将“交叉验证”作为一个独立的执行步骤。ReAct 则可能交叉验证和查找混在一起，逻辑不清，效率也低。

**项目联系：**
您的项目可以这样描述：“我在设计一个‘智能数据分析报告 Agent’，用户只说‘分析上季度的销售数据’。我采用 Plan-and-Execute 模式。Agent 首先规划：1. 查询上季度销售数据库，2. 对数据进行统计分析，3. 生成可视化图表，4. 撰写分析报告。每一步单独执行、可监控。如果第一步查询数据库失败了，我会触发一个‘失败恢复’流程，再次规划如何获取数据（如改查询缓存），而不是从头开始。”

    1.  **题目**：你提到有时候需要手搓 Agent，而不完全依赖框架如 LangChain，能结合项目讲讲你的判断依据吗？
        - **对应参考答案**：
            “用框架可以快速原型，但到了生产环境，我会仔细考虑三点。第一，**调试和可控性**：框架的抽象层过多，当 Agent 行为异常时，我无法直接在底层干预，需要绕很多弯子才能加一个日志或改一个逻辑。手搓的话，我可以用一个 `while` 循环 + `if-else` 就控制住了。第二，**性能开销**：框架本身执行流程有固定的开销，对于毫秒级性能敏感的场景，轻量级的手搓方案没有这些冗余。第三，**特殊需求**：如果我们的 Tool Calling 涉及复杂的原子化事务（比如数据库操作需要 ACID），框架的 Tool 机制无法保证，就必须手写代码来确保整个流程的安全性和一致性。所以，我的原则是‘原型用框架，上线看场景’。”

## 3. 今日必背问答卡片

1.  **Q：** 如何防止 Agent 短期记忆互相污染？
    - **A：** 要为每个用户会话创建一个独立的 Session ID。短期记忆（对话历史）存储在 Redis 或内存中以 Session ID 为 key 的数据结构中，确保用户 A 的对话只在 Session A 的上下文中。
    - **一句话记忆法：** “一人一证，对号入座，绝不串门。”
    - **复习标签：** #Agent #Memory #状态管理

2.  **Q：** 在 Agent 中，Plan-and-Execute 遇到步骤执行失败，如何设计错误恢复？
    - **A：** 最常见的是“重新规划”策略。将失败信息、当前已完成的状态和目标，一起交给模型，让它重新生成一个完整的计划。高级做法是“部分重新规划”，只从失败点开始往后修正，效率更高。
    - **一句话记忆法：** “计划赶不上变化，那就撕了重写。（或者只撕当前页）”
    - **复习标签：** #Agent #Plan-and-Execute #错误恢复

3.  **Q：** 什么是 Rerank 在 RAG 中的作用？为什么它是必要的？
    - **A：** 向量检索（第一轮）是高效的“大海捞针”，但可能捞上来和问题语义相似但无关的“噪声”。Rerank 用 Cross-Encoder 模型（如 BGE-Reranker）对 Top-K 检索结果做一次更精准的“精排”，能显著提升输入给大模型的上下文质量，是提高答案准确率和 Faithfulness 的关键一环。
    - **一句话记忆法：** “粗筛是沙里淘金，精排是火眼金睛。”
    - **复习标签：** #RAG #Rerank #检索优化

4.  **Q：** 模型部署时，vLLM 的 PagedAttention 和 SGLang 的 RadixAttention 核心区别是什么？
    - **A：** 两者都是为了高效管理 KV Cache。PagedAttention 关注 GPU 显存的碎片化问题，通过“分页”管理显存。而 RadixAttention 更关注 Compute Cluster（计算集群/节点）的复用，通过 radix tree 自动发现和共享 prompt 前缀，特别适合 Alpaca 这种有固定 prompt 前缀的 Prompt Pooling 场景，能大幅降低 TTFB（首token延迟）。
    - **一句话记忆法：** “vLLM 重在省内存，SGLang 重在省计算。”
    - **复习标签：** #模型部署 #vLLM #SGLang #推理优化

5.  **Q：** 在海量文档 RAG 中，如何处理“Lost in the Middle”问题？
    - **A：** 精简和排序。首先，不是 Top-K 越多越好，应严格控制 K 值（如 3-5）。其次，检索到的 chunks 按重要性（如分数）降序排列，把最相关的内容放在 prompt 的最前面。最后，如果 chunk 太长，可以先用模型做摘要再拼入 prompt。
    - **一句话记忆法：** “宁缺毋滥，好酒先上。”
    - **复习标签：** #RAG #LostInTheMiddle #上下文优化

## 4. 今日面试专项训练

### 4.1 大模型理论追问题

**问题：** 在你设计的带记忆 Agent 中，如果模型出现了“记忆幻觉”，即它生成的回答所依据的“记忆”是被模型错误构造或曲解的，而非真实的历史。你认为最可能的原因是什么？从流程和评测上你如何系统性地排查和缓解？

**面试口头版参考答案：**
“我很认同您的观点，这叫‘记忆幻觉’。我认为最可能的原因是**记忆检索失败**：要么是错误地检索到了不相关的记忆，要么是模型在提取记忆时的 prompt 引导不够好，导致提取了错误视角的信息。排查上，我会先做`Ablation Study`——把记忆模块关掉，只靠当前 query，看看问题是否还存在。如果关了反而好了，说明记忆模块是噪声源。然后我会检查上线 trace，看模型具体检索到了哪些记忆条目，以及它的推理链（Thought，如果有的话），定位到底是哪里开始歪的。缓解上，我在记忆注入上下文时，不仅给内容，还会给置信度标签，并在 System Prompt 里强调‘仅当记忆与当前问题高度相关，且你有信心时，才使用它，否则以当前上下文为准’。”

**深入理解版参考答案：**
“这是一个非常深入的问题，触及了 Agent 的核心信任问题。‘记忆幻觉’的产生根源在于**模型对记忆的过度信任或错误整合**，即使记忆本身是真实的。

1.  **根因分析**：
    *   **检索端失败**：检索出的记忆条目与当前 Query 语义无关，但模型为了完成任务，强行关联。
    *   **记忆端噪声**：在记忆提取阶段，模型错误地提取了对话中的次要信息，比如把用户的玩笑话当成了事实偏好记录下来。
    *   **模型端倾向**：大模型有“过度拟合上下文”的倾向，如果 prompt 里给了好几条记忆，它往往会倾向于使用并提供支持性证据，即使这些证据是它自己引用错误的。
    *   **信息融合困难**：当当前上下文和记忆存储的信息存在微妙差别或更新时，模型可能没有进行正确的“冲突仲裁”，而是随意将新旧信息揉合。

2.  **系统性排查与评测**：
    *   **离线评测（构建专测集）**：
        *   **记忆检索评测**：构建 `{Query, 预期相关记忆条目}` 对，评估检索系统的召回率，看是否总是找不对记忆。
        *   **记忆注入评测**：将正确的记忆注入，但要求模型回答一个与记忆有细微冲突的问题，看模型是忠实于记忆，还是能正确判断“新信息优先”。这是评测冲突仲裁能力。
    *   **在线可观测性**：
        *   在 Agent 的日志接口中，必须**显式输出**“模型看到的记忆列表”和“模型最终使用的记忆”。通过对比，可以快速判断模型是检索失败还是使用失败。
    *   **Ablation Test（消融实验）**：
        *   **Step 1**：只跑基础 RAG，不注记忆。
        *   **Step 2**：注入正确的记忆。
        *   **Step 3**：注入带噪声的记忆。
        *   通过对比三者的答案质量（Faithfulness / Accuracy），可以定向归因“记忆模块”带来的收益和风险。

3.  **缓解策略**：
    *   **Prompt 重塑**：在 prompt 中明确记忆的优先级。例如：“你拥有来自用户历史的背景信息。在使用这些信息时，请务必结合当前问题。如果当前问题或上下文提供了更新的信息，请优先遵循当前信息。”
    *   **置信度打分**：在检索到记忆后，使用一个简单的模型对“记忆与当前查询的相关性”进行评分，设定一个阈值，只将高相关性的记忆送给下游。
    *   **强制反思**：让模型在使用记忆前，先执行一个步骤：“基于当前问题和对话上下文，我需要使用哪条记忆？这条记忆真的和用户的问题相关吗？”。这增加了推理透明度。
    *   **后处理校验**：在生成最终回答后，用另一个轻量模型检测：回答中提到的任何事实，是否都能在‘当前上下文’或者‘被使用的记忆’里找到明确的证据？如果找不到，则禁止输出或让模型修改。”

**可能追问与回答：**
- **追问**：你提到了“置信度打分”来过滤记忆，这个分数如何定义和获取？
    - **简短回答**：可以由一个专门的打分模型（或直接用 LLM）来评估“检索到的记忆条目与当前用户 query”的语义相关性。或者，更简单一些，可以利用检索系统的相似度分数（如 cosine similarity），设置一个经验阈值（如 0.7）。低于此阈值的记忆就过滤掉。
- **追问**：如果模型通过反思步骤后，仍然给出了错误的回答，你怎么继续迭代优化？
    - **简短回答**：这是 Bad Case 闭环最核心的价值。这种情况下，我会把这一轮对话、Agent 的内部 Thought、使用的记忆和最终回答全部记录下来作为 Bad Case。然后人工分析：是反思 prompt 写得不够好（模型没有真的反思），还是系统 prompt 本身就需要调整？或者，我需要增加一个**纠正循环**，即当模型输出后，由一个校验 Agent 来审查其 Faithfulness，如果审查不通过，则要求生成 Agent 重新生成。
