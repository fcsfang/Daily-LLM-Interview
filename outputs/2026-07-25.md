### 题目 1：如何设计多用户并发 Agent 的 Memory 隔离与状态管理？

**来源依据：**
- AgentGuide 面经总结 - https://github.com/adongwanai/AgentGuide/blob/main/docs/04-interview/12-company-interview-cases.md - 面经或社媒 - 需进一步验证
- AI 应用开发面试题库 - https://github.com/didilili/ai-agents-from-zero/blob/main/AI%E6%99%BA%E8%83%BD%E4%BD%93%E4%B8%8E%E5%A4%A7%E6%A8%A1%E5%9E%8B%E5%BA%94%E7%94%A8%E5%BC%80%E5%8F%91%E9%9D%A2%E8%AF%95%E9%A2%98%E5%BA%93.md - 面经或社媒 - 需进一步验证

**可信度：** 中

**考察点：** Agent 系统设计、多用户隔离、Memory 结构、线程安全

**面试口头版回答：**
设计多用户并发的 Agent Memory，核心原则是“用户级的隔离 + 分层存储”。短期记忆（对话上下文）用 Redis 或内存缓存按 session_id 做 key-value 隔离，每次请求从用户上下文池中加载。长期记忆（用户画像、偏好、历史摘要）使用向量数据库或关系数据库，每条记录绑定 user_id。关键要注意线程安全：如果使用 Python 全局变量存 memory，必须加锁或用 asyncio 的上下文变量；更推荐用无状态设计，把 memory 存在外部存储中，每个请求独立拉取。另外，需要防止 memory 泄露——设置过期策略和上限，例如短期记忆最多保留最近 20 轮对话，长期记忆定期摘要压缩。这样既能保证隐私隔离，又能支撑高并发。

**深入理解版回答：**
多用户并发场景下，Memory 的设计直接决定 Agent 系统的稳定性和数据安全。业界常用方案是分层架构：短期记忆（Short-term Memory）存放当前会话的轮次消息和中间状态，通常使用 Redis 哈希表，键为 session_id，值为 JSON 序列化的消息列表。每次请求来临时，从 Redis 读取当前会话上下文，注入到 LLM 的 prompt 中。注意需要给每个 session 设置 TTL（比如 30 分钟无操作自动清除），防止内存爆炸。长期记忆（Long-term Memory）存放用户偏好、历史任务结果、知识沉淀，使用向量数据库（如 Milvus、Pinecone）或传统数据库，每条记录带 user_id 和 timestamp 标签，检索时按用户过滤。对于冲突更新，可以使用乐观锁（版本号）或最后写入者获胜策略。线程安全方面，如果使用 LangChain 的默认 Memory（如 ConversationBufferMemory），它在多线程环境下是共享状态，必须改为每个用户实例化一个 memory 对象，或者在服务层做请求级别的隔离。更工程化的做法是使用像 Ray 这样的分布式计算框架，每个用户请求 worker 独立，天然隔离。此外，还需要日志审计，记录每个用户的 memory 操作，方便回滚和排查。

**常见追问与回答：**
- **追问：** 如果用户并发非常高，Redis 成为瓶颈怎么办？  
  回答：可以引入本地内存缓存（如 LRU Cache）做一级缓存，减少 Redis 读取次数；同时将 Memory 内容分段，只加载最近几轮对话到本地，历史内容延迟加载。
- **追问：** 如何确保长期记忆的隐私？比如用户 A 通过相似向量检索到了用户 B 的信息？  
  回答：在向量数据库的 query 中强制加入 user_id 过滤器（类似 SQL WHERE），同时索引也要按照 user_id 分片，从数据层面杜绝跨用户访问。

**项目联系：**
在构建多租户客服 Agent 时，需要为每个用户维护独立的对话历史和偏好。我采用了 Redis 按用户 session 存储短期记忆，同时用 PostgreSQL 存储长期用户特征（如购买倾向），每次工具调用时先检查该用户的历史行为，避免推荐冲突。并发测试中通过加 Redis atomic 操作解决了状态冲突问题。

**记忆关键词：**
#Memory隔离 #用户级 #线程安全 #Redis #长期记忆 #短期记忆

### 题目 2：你如何设计和迭代 Agent 的 System Prompt？有没有做过 Prompt 自动优化？

**来源依据：**
- 字节 Agent 开发面经 - https://github.com/adongwanai/AgentGuide/blob/main/docs/04-interview/12-company-interview-cases.md - 面经或社媒 - 需进一步验证
- AI 应用开发面试题库 - https://github.com/didilili/ai-agents-from-zero/blob/main/AI%E6%99%BA%E8%83%BD%E4%BD%93%E4%B8%8E%E5%A4%A7%E6%A8%A1%E5%9E%8B%E5%BA%94%E7%94%A8%E5%BC%80%E5%8F%91%E9%9D%A2%E8%AF%95%E9%A2%98%E5%BA%93.md - 面经或社媒 - 需进一步验证

**可信度：** 中

**考察点：** Prompt 工程、迭代方法、自动优化、不完整请求补全

**面试口头版回答：**
我的 Prompt 迭代方法分三步：第一，从最小可用版本出发，先写一个能跑通的初始 prompt，包含角色定义、任务目标、工具调用格式和输出约束。第二，通过日志和 bad case 分析，不断添加防错指令和边界条件。比如发现工具调用格式容易出错，就在 prompt 里加一句“必须输出 JSON 格式，且只包含一个 action”。第三，引入 A/B 测试和自动化评估——用 LLM-as-Judge 对比不同版本在测试集上的准确率。关于自动优化，我尝试过 DSPy 框架，它通过优化器自动调整 prompt 模板，但生产环境我更倾向于手动控制，因为自动优化可能导致过拟合。当用户请求不完整时，我采用“反问 + 默认值”策略：先让 LLM 判断是否缺少关键信息，如果是，则生成追问；如果信息缺失但可以推测，则用默认值填充并提示用户。这样能提高交互流畅度。

**深入理解版回答：**
System Prompt 的设计本身就是迭代式的工程。我分为四个阶段：  
1. **基线和纠错**：第一个版本通常来自官方示例或开源项目，然后跑几百条测试数据，人工标注 bad case，总结出常见的错误模式，比如指令遵循失败、格式错误、幻觉、安全越权等。每类问题对应一个 prompt 修复，例如在 prompt 中加入“不要执行任何自增或删除操作”。  
2. **结构化与版本管理**：将 prompt 分为静态部分（角色、规则）和动态部分（工具描述、示例）。静态部分用 Git 管理版本，每次修改附带 diff 和效果摘要。动态部分从工具数据库自动渲染，避免手动更新。  
3. **自动优化**：除了 DSPy，我还使用过“Prompt 敏感性分析”——对 prompt 中关键词做随机替换，观察输出变化，找出关键约束。但自动调优有风险，比如过度优化导致对特定输入泛化差。所以我更倾向于“半自动”：机器推荐改法，人工审核后上线。  
4. **不完整意图补全**：在 prompt 中显式要求 LLM 先判断用户问题是否信息充分，如果缺失，则输出“ASK: 具体缺失字段”。后端收到 ASK 后，返回给前端让用户补充。如果是模糊请求（如“查一下最近的订单”），模型可自动假设最近 7 天，并在回答后附加“如需精确查询请指定日期范围”。  

**常见追问与回答：**
- **追问：** Prompt 版本如何做回滚？  
  回答：每个 prompt 版本保存到配置中心（如 Apollo），带有生效环境（dev/test/prod），可通过开关快速切换。回滚时只需将生产环境配置指向上一个稳定版本。
- **追问：** 自动优化时如何防止过拟合到测试集？  
  回答：使用独立验证集和测试集；优化器限制搜索次数；每次优化后人工抽查 50 个 hard case。

**项目联系：**
在金融合规 Agent 项目中，我负责 prompt 维护。最初模型总在输出中泄露客户账户号，我在 prompt 中加了“禁止输出任何个人身份信息，用 masked 代替”，并用脚本检测输出中的敏感模式，迭代到第三个版本后敏感信息泄露降为零。

**记忆关键词：**
#Prompt迭代 #badcase闭环 #自动优化 #补全意图 #版本管理 #A/B测试

### 题目 3：如何为大模型应用设计可观测性系统？需要监控哪些指标？如何通过日志和 trace 定位 bad case？

**来源依据：**
- AI 应用开发面试题库 Q1-5 - https://github.com/didilili/ai-agents-from-zero/blob/main/AI%E6%99%BA%E8%83%BD%E4%BD%93%E4%B8%8E%E5%A4%A7%E6%A8%A1%E5%9E%8B%E5%BA%94%E7%94%A8%E5%BC%80%E5%8F%91%E9%9D%A2%E8%AF%95%E9%A2%98%E5%BA%93.md - 面经或社媒 - 需进一步验证

**可信度：** 中

**考察点：** 日志、监控、trace、延迟、效果指标、bad case 闭环

**面试口头版回答：**
大模型应用的可观测性需要覆盖效果、性能、成本、稳定性四个维度。效果方面，监控准确率、忠实度（用 LLM-as-Judge 打分）、引用正确率；性能方面，首 token 延迟、端到端延迟、P95/P99；成本方面，token 消耗、API 调用次数；稳定性方面，超时率、重试率、降级率。核心是通过结构化日志和分布式 trace 来串联每次请求的完整链路——从用户输入到检索、推理、输出，每一步都记录耗时、输入输出、工具调用结果和异常。定位 bad case 时，先看效果指标异常（如分数低于阈值），然后通过 trace 找到具体节点：如果是检索失败，查召回文档质量；如果是推理问题，看 prompt 和模型输出。我会定期将 bad case 聚类，形成一个“bad case 池”，更新回归测试集。日志系统我用 ELK 或 Grafana Loki，trace 用 OpenTelemetry，Alert 用 Prometheus + AlertManager。

**深入理解版回答：**
可观测性在 LLM 应用中比传统微服务更复杂，因为模型输出是概率性的。我建议分层构建：  
1. **基础设施层**：记录 CPU/GPU 使用率、内存、网络，用 prometheus 采集。  
2. **应用层**：每个请求分配唯一 trace_id，所有组件（检索、rerank、LLM 调用、工具执行）都上报 span。包含：输入（query）、输出（response）、prompt 模板版本、模型参数（temperature）、耗时、token 数、错误码。  
3. **效果层**：定期采样（如 10% 的流量），调用 LLM-as-Judge 对回答打分（正确性、帮助性、安全性）。分数同样打上 trace_id，可以关联到具体请求。  
4. **成本层**：累计每个用户的 token 消耗，设置预算告警。  

定位 bad case 的流程：从监控面板发现正确率突然下降 -> 按时间窗口筛选 trace_id -> 打开日志，查看模型输出是否偏离预期 -> 查看检索到的文档是否相关 -> 检查工具调用是否失败 -> 进一步查看 prompt 版本是否被修改 -> 如果是，回滚并分析 diff。  

我还设计了 bad case 自动化入库：通过规则（如输出包含“抱歉我无法回答”或用户反馈差评）自动触发采样，将对应的完整 trace 保存到 MongoDB，供后续分析和模型迭代。

**常见追问与回答：**
- **追问：** 如何区分是模型问题还是检索问题？  
  回答：在 trace 中，如果检索到的文档质量高但模型输出错误，是生成问题；如果检索到的文档本身不相关，是检索问题。可以额外保存 retrieval score，便于区分。
- **追问：** 日志和 trace 会不会对性能产生负担，尤其是高并发？  
  回答：使用异步日志框架（如 loguru），同时采用采样策略——对正常流量采样 1%，对异常流量全量记录。trace 使用 OpenTelemetry 的尾部采样（tail-based sampling），只保留错误或慢请求的完整链。

**项目联系：**
在智能客服 Agent 项目中，我们搭建了基于 OpenTelemetry + Grafana 的可观测性平台。通过分析 trace，发现某些地区用户请求超时比例高，是因为使用了慢的 embedding 模型且没有缓存，于是加入了 embedding 缓存，P95 延迟降低 40%。

**记忆关键词：**
#可观测性 #trace #badcase #LLM-as-Judge #日志 #性能指标

### 题目 4：Workflow 与 Agent 的本质区别是什么？在实际项目中如何选择？

**来源依据：**
- AI 应用开发面试题库 Q1-3 - https://github.com/didilili/ai-agents-from-zero/blob/main/AI%E6%99%BA%E8%83%BD%E4%BD%93%E4%B8%8E%E5%A4%A7%E6%A8%A1%E5%9E%8B%E5%BA%94%E7%94%A8%E5%BC%80%E5%8F%91%E9%9D%A2%E8%AF%95%E9%A2%98%E5%BA%93.md - 面经或社媒 - 需进一步验证
- AgentGuide 面经总结 - https://github.com/adongwanai/AgentGuide/blob/main/docs/04-interview/12-company-interview-cases.md - 面经或社媒 - 需进一步验证

**可信度：** 中

**考察点：** 工作流编排、Agent 选型、工程判断、边界意识

**面试口头版回答：**
Workflow 是“定路径”的执行引擎，所有节点和分支在运行前确定；Agent 是“选路径”的智能体，每步通过 LLM 决策下一步动作。选择时核心看流程是否固定。如果业务流程稳定，如“接收工单->校验->分类->分派”，用 Workflow 保证稳定高效、可审计；如果任务开放，如“用户抛一个模糊需求，需要动态调用多个工具”，用 Agent 灵活决策。实际项目中经常混合使用：在主流程上用 Workflow 兜底关键步骤，在某个复杂子任务上用 Agent。比如客服系统，先用 Workflow（基于规则）判断用户意图是否为“查订单”，是则进入订单查询 Agent，Agent 再决定调用哪个 API。关键设计点包括：状态传递（Workflow 上下文如何传给 Agent）、超时与回退（Agent 循环超限则降级到 Workflow 的默认分支）。

**深入理解版回答：**
Workflow（工作流）和 Agent 在架构上的分界线就是“决策点是否在设计时确定”。  
- **Workflow**：用 DAG 定义步骤，每个节点可能调用 LLM、API、规则引擎。常见框架 LangChain 的 LCEL、Temporal、Airflow。优点是可可视化、可审计、执行确定性强、容易保障 SLA。缺点是无法应对预料之外的路径。  
- **Agent**：模型根据当前状态选择工具和下一步。框架如 LangGraph、AutoGen。能处理动态任务，但存在不可控性，比如死循环、幻觉、工具误用。  

选型决策矩阵：
| | 路径固定 | 路径动态 |
|---|---|---|
| 单步骤 | Prompt + RAG | Agent（最小版本） |
| 多步骤 | Workflow | Agent（带 Planner） |

工程上更稳妥的做法：**Workflow 为主，Agent 为辅**。例如，用 Workflow 实现核心业务逻辑（如资金转账），用 Agent 处理异常情况的降级策略。我还遇到过一个例子：电商优惠券发放，流程在 Workflow 中写死，但其中“判断用户是否合适领取”这个子任务用了 Agent 来推理用户画像和购物行为，因为规则难以穷举。

**常见追问与回答：**
- **追问：** 如果 Agent 在 Workflow 中运行超时怎么办？  
  回答：设置 Agent 执行的最大步数和超时时长，超时后 Workflow 切换到一个预设的 fallback 分支，比如直接请人工介入或输出通用回复。
- **追问：** 如何保证 Workflow 的可观测性？  
  回答：每个节点都记录入参、出参、耗时、错误，Workflow DAG 本身就是一个天然 trace。用 OpenTelemetry 给 workflow 实例全局 ID，可以追踪每一步执行情况。

**项目联系：**
在构建企业助手 Agent 时，为了处理“请假审批”流程，我使用了 Workflow 定义“提交->主管审批->HR 审批”，但在“主管审批”环节，如果主管回复“帮我看看同事张三的剩余假期”，则触发 Agent 子任务去查询数据库，返回后继续 Workflow。这样既保证审批流程合规，又允许人类自然语言交互。

**记忆关键词：**
#Workflow #Agent #选型 #确定性 #动态决策 #混合架构

### 题目 5：如何设计 Agent 的工具调用安全机制？防止模型滥用工具或越权操作？

**来源依据：**
- AgentGuide 面经总结 - https://github.com/adongwanai/AgentGuide/blob/main/docs/04-interview/12-company-interview-cases.md - 面经或社媒 - 需进一步验证
- AI 应用开发面试题库 - https://github.com/didilili/ai-agents-from-zero/blob/main/AI%E6%99%BA%E8%83%BD%E4%BD%93%E4%B8%8E%E5%A4%A7%E6%A8%A1%E5%9E%8B%E5%BA%94%E7%94%A8%E5%BC%80%E5%8F%91%E9%9D%A2%E8%AF%95%E9%A2%98%E5%BA%93.md - 面经或社媒 - 需进一步验证

**可信度：** 中

**考察点：** 权限控制、安全、工具调用、降级策略

**面试口头版回答：**
Agent 的工具调用安全需要从三个层面设计：输入过滤、执行权限和事后审计。首先，在 prompt 中明确定义工具的使用范围，比如“只允许查询当前用户的订单，不允许修改或删除”，并且对用户输入做脱敏和注入检测。其次，在执行层，为每个工具设置白名单参数和权限标签，比如“发送邮件”工具只允许发送到用户自己的邮箱，限制最大收件人数。同时，所有工具调用必须通过一个统一的“网关”来鉴权和限流，工具返回值也要过滤敏感字段（如密码、保险号）。最后，建立审计日志，记录每次工具调用及其输入输出，便于追溯异常。如果检测到模型试图调用越权工具，可以触发降级：拒绝操作并返回友好提示，同时记录日志告警。另外，为防止循环调用导致无限扣费，每个工具设置调用次数上限和超时。

**深入理解版回答：**
安全是 Agent 上线的第一关。我通常按照“预防-检测-响应”框架设计：  
**预防**：  
- 工具描述中显式标注权限等级（如 readonly、write、admin）。  
- 使用 Pydantic 对工具输入做 schema 校验，限制参数类型、长度、正则。例如，用户 ID 必须符合 uuid 格式，邮箱参数必须匹配正则。  
- 动态注入用户上下文：工具函数接收用户身份信息（从 token 解析），在函数内部再做一次二次校验，确保不越权。  
**检测**：  
- 使用一个“安全分类器”对模型的工具选择做实时评分，如果模型选的工具与历史模式差异过大，触发告警。  
- 设置频率限制：同一用户 1 分钟最多调用 10 次写操作。  
**响应**：  
- 拒绝操作时，返回一个自定义错误码，Agent 根据错误码重新决策或向用户说明。  
- 将异常调用记录到安全事件表，定期分析模式，更新 prompt 或工具定义。  

工程上我还会在 Agent 的 planner 和执行器之间插入一个“安全过滤器”层，它不是一个 LLM，而是一个规则引擎 + 少量 ML 模型，低延迟、高可靠。

**常见追问与回答：**
- **追问：** 如果模型通过 prompt 注入尝试绕过限制怎么办？  
  回答：除了 prompt 层面的约束，更底层的工具网关必须独立校验权限，模型输出只是建议，网关是最终执行者。同时对模型输入做恶意检测（如 huggingface 的 jailbreak classifier）。
- **追问：** 多 Agent 场景下怎么保证互信？  
  回答：每个 agent 分配证书，Agent 之间通信使用加密通道，并且通过消息队列进行异步调用，主 Agent 授权子 Agent 执行特定任务时附带 token，子 Agent 拿 token 去工具网关鉴权。

**项目联系：**
在医疗咨询 Agent 中，工具包括“查询病历”、“预约挂号”、“发送处方”。我设计了工具权限矩阵：普通用户只能查询自己的病历和预约，医生可查询患者病历但不能开处方，只有在确诊流程后才能调用开处方工具。所有调用都写入 audit_log，供医院合规审查。

**可转化面试题：**
1. RAG 知识库中的文档更新了，如何进行增量更新而不重建全量索引？
2. 全量 SFT 和 LoRA SFT 的 lr 设置有什么经验和技巧？

**对应参考答案：**

**问题 1 答案：**
核心是用哈希检测文档变化。先将文档分 chunk，每个 chunk 计算一个哈希值（如 md5）并存储。当文档更新时，重新计算新文档的 chunk 及其哈希，与旧哈希对比。对于没有变化的 chunk，保留原有向量；对于新增或修改的 chunk，重新 embedding 并 upsert 到向量数据库；对于删除的 chunk，从数据库删除对应向量。注意：更新文档后 chunk 边界可能改变（比如原 chunk “A+B”变成“A”和“B”），所以不能只更新单条记录，需要先根据 document_id 删除所有旧 chunk，再插入新 chunk。参考资料[5]中“小米的经典面试题”的讨论。

**问题 2 答案：**
全量 SFT 通常使用较小的学习率（如 2e-5 到 5e-5），因为更新全部参数需要稳定。LoRA SFT 可以用稍大的学习率（如 1e-4 到 5e-4），因为只更新低秩矩阵，稳定性更好。技巧是：先做预热（warmup），比如前 100 步从 0 线性增加到目标 lr；然后配合余弦退火衰减。LoRA 的 alpha 通常设为 rank 的 2 倍，但实验发现对于 7B 模型，rank=16 时 lr=3e-4 效果较好。需要根据 loss 曲线调整：如果 loss 震荡，降低 lr；如果收敛太慢，提高 lr。

## 4. 今日面试专项训练

### 4.1 大模型理论追问题

**问题：** 在 Agent 系统中，如何设计 Prompt 质量评估实验流程？请从指标选取、实验分组、数据标注、统计分析四个方面展开，并说明如何平衡自动化评估与人工评估的优缺点。

**面试口头版参考答案：**
我设计 Prompt 评估流程分为四步。第一，指标选取：核心用任务完成率（是否成功调用工具并返回合理结果）、格式正确率（工具调用 JSON 是否合法）、以及用户满意度（通过后置问卷或 LLM-as-Judge 打分）。对于安全类任务，额外监控违规模块比例。第二，实验分组：将流量随机分叉为两组或多组（A/B testing），每组用不同 prompt 版本，保证用户特征一致。第三，数据标注：自动化评估用 LLM-as-Judge 先初筛，人工抽样 10% 验证；对于开放式问答，必须人工标注。第四，统计分析：用假设检验（如卡方检验）判断差异显著性，同时关注效果和成本的 trade-off。自动化评估快但可能偏差（如偏好自己风格），人工评估准确但昂贵，所以组合使用：自动化做大样本筛选，人工做小样本验证+bad case 分析。

**深入理解版参考答案：**
Prompt 评估是迭代优化的闭环。具体实验设计如下：  
1. **指标选取**：除了常见的任务完成率和忠实度，还要关注“鲁棒性”——对 prompt 微小扰动的稳定性。我会构建一个“对抗性测试集”，如输入同义但格式不同的查询，看 prompt 是否稳定。  
2. **实验分组**：使用分桶实验（bucket test），每个用户固定分配到一个 prompt 版本，避免交叉污染。样本量需要事先计算，保证统计功效（power analysis）。  
3. **标注策略**：自动化评估我使用两种方法：a) 基于规则（如检测 JSON 格式）；b) 基于 LLM（用 GPT-4 作为裁判，给定评分准则）。人工标注由 3 人独立标注，取多数或均值，评估一致率（Kappa 系数）。  
4. **统计分析**：连续指标（如延迟）用 t 检验或 Mann-Whitney U 检验；离散指标（如任务成功率）用卡方检验。如果 p<0.05 且效应量（effect size）大于预设最小可检测差异，则判定为显著改进。  

自动化评估的优势在于成本低、可大规模重复；劣势是 LLM-as-Judge 可能偏好特定风格，且对创造性任务评估不准。人工评估优势是准确度高，劣势是成本贵、耗时。**折中方案**：每次 prompt 修改，先跑自动化测试集（200 条），分数提升 >5% 且无 regression 案例，再提交人工验证（20 条），通过后全量上线。这样既保证效率又避免盲信自动评分。

**可能追问与回答：**

- **追问：** 如果自动评分和人工评分出现大幅不一致，你如何处理？  
  回答：首先检查评分准则是否一致，然后看冲突案例的模式。常见场景是 LLM-as-Judge 对“安全拒绝”的回答打分低，但人工认为符合要求。此时需要调整自动评分 prompt，加入安全准则的权重，或者对这类 case 直接采用人工评分。同时将冲突案例加到训练集中迭代裁判模型。

- **追问：** 样本量少时（如只有 50 条测试数据），如何保证实验结论可靠？  
  回答：样本少时统计显著性可能不够，我会采用 bootstrap 方法（自助法）估计效果差异的置信区间。同时结合定性分析，人工检查所有差异 case。另外，小样本实验更适合做探索性分析（exploratory），而非确认性分析（confirmatory）。建议先积累足够样本再下结论。
