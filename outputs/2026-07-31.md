## 1. 今日面试真题精讲

### 题目 1：KV Cache 是什么？为什么能极大地提升推理速度？

**来源依据：**
- [AgentGuide 面试案例（GitHub）](https://github.com/adongwanai/AgentGuide/blob/main/docs/04-interview/12-company-interview-cases.md) - 面经或社媒 - 需进一步验证
- [2026大厂大模型/Agent面试题（CSDN/AtomGit）](https://gitcode.csdn.net/6a236d7b662f9a54cb7a2bf1.html) - 面经或社媒 - 需进一步验证

**可信度：**
中（面经汇总中反复出现的高频题，多家公司均有提及）

**考察点：**
KV Cache 原理、Prefill/Decoding 两阶段、显存估算、推理优化工程手段

**面试口头版回答：**
KV Cache 的核心思路是“空间换时间”。自回归生成分两个阶段：Prefill 阶段一次性算出 prompt 全部 token 的 K 和 V；Decoding 阶段每生成一个新 token，只计算当前 token 的 K/V，再与缓存的 K/V 做注意力计算。没有 KV Cache 的话，每个新 token 都要重算前面所有 token 的 K/V，Decoding 复杂度是 O(n²)；有缓存后单步注意力复杂度降到 O(n)，生成速度大幅提升。工程上要注意缓存很占显存：7B 模型在 2048 token 单序列下约 1GB，所以要用 PagedAttention 按页分配减少碎片，这也是 vLLM 吞吐高的核心原因。

**深入理解版回答：**
KV Cache 是部署面试必考题，回答要覆盖三层：

1. **原理层**：自回归生成是逐 token 的。第 t 步的注意力需要第 t 步的 Q 与之前所有 token 的 K/V 做点积。如果没有缓存，每一步都要把历史 token 的 K/V 重新计算一遍，累计计算量随序列长度平方级增长。缓存后，每步只需要新增当前 token 的 K/V，计算量变为线性。

2. **显存层**：KV Cache 大小 = 2（K 和 V）× 层数 × KV 头数 × 头维度 × 精度字节 × 序列长度 × batch 数。以 LLaMA-2-7B 为例：32 层、GQA 8 组、头维度 128，FP16 下每 token 约 128KB（2×32×8×128×2 字节）；2048 token 单序列约 256MB，batch 8 时约 2GB。如果没有 GQA（32 个 KV 头），每 token 是 512KB，翻 4 倍。

3. **工程层**：vLLM 的 PagedAttention 把 KV Cache 按固定大小的 block 分配，类似操作系统分页，按需分配物理块、减少碎片和预分配浪费，从而支持更大 batch，提升吞吐。SGLang 的 RadixAttention 复用公共前缀（如多轮对话中相同的 system prompt），减少重复计算。PD 分离则把 Prefill 和 Decoding 部署到不同 GPU 上——Prefill 是计算密集，Decoding 是显存带宽密集，分离后可独立扩缩容。

常见坑：只说“KV Cache 能加速”而不说显存代价；不区分 Prefill 和 Decoding 的资源特征；忽略 GQA 对 KV Cache 规模的巨大影响。

**常见追问与回答：**

Q1：KV Cache 的显存如何估算？
A：公式是 2 × 层数 × KV 头数 × 头维度 × 精度字节 × 序列长度 × batch。7B GQA 模型 FP16 下约 128KB/token，2048 token 单序列约 256MB；非 GQA 则乘以 KV 头数比例，通常大 4 倍。

Q2：KV Cache 太大导致 OOM 怎么办？
A：四个手段：GQA/MQA 降低 KV 头数、KV Cache INT8 量化、PagedAttention 分页管理、PD 分离。优先做量化，因为对模型结构无侵入。

Q3：为什么 PagedAttention 能提升吞吐？
A：传统方案按最大序列长度预分配连续显存，碎片多、浪费大；PagedAttention 按固定大小块分配，需要时才分配物理块，显存利用率显著提升，支持更大 batch，从而提升吞吐。

**项目联系：**
在部署项目里，可以先按公式估算部署模型的 KV Cache 峰值，再用 vLLM 配置 gpu_memory_utilization 并留 10%-20% 余量。实际压测时对比开/关 PagedAttention 的吞吐变化，把数据和 vLLM 日志中的 KV Cache 池大小对照，面试时说出“我的显存估算和实测差距在 10% 以内”，比单纯背概念更有说服力。

**记忆关键词：**
KV Cache、Prefill、Decoding、PagedAttention、显存估算、空间换时间

### 题目 2：如何降低大模型 API 服务的推理延迟和成本？

**来源依据：**
- [B站“大模型面经”系列视频（含“如何降低大模型API服务的推理延迟和成本”）](https://www.bilibili.com/video/BV18gsdznEZX) - 其他（视频） - 需进一步验证
- [AgentGuide 面试案例（GitHub）](https://github.com/adongwanai/AgentGuide/blob/main/docs/04-interview/12-company-interview-cases.md) - 面经或社媒 - 需进一步验证

**可信度：**
中（面经常见场景题，多家公司考察）

**考察点：**
延迟指标拆解（TTFT/TPOT）、Continuous Batching、语义缓存、量化/蒸馏、成本控制思维

**面试口头版回答：**
降低延迟和成本需要从端到端链路找瓶颈，我一般分四个层面。第一，推理引擎层：用 vLLM 或 SGLang，开 Continuous Batching 和 PagedAttention，把 GPU 利用率拉满，这是吞吐提升的关键。第二，模型层：能用小模型就不上大模型，或者对模型做 INT8/INT4 量化和蒸馏，直接降低计算和显存带宽需求。第三，服务层：加语义缓存，高频相似问题直接命中缓存，不跑模型，延迟几乎为零。第四，部署层：PD 分离和弹性扩缩容，把 Prefill 和 Decoding 分开部署，避免互相拖累。另外延迟一定要拆成 TTFT 和 TPOT 两个指标分别定 SLO，不能混在一起调。

**深入理解版回答：**

这个问题的核心是“先拆指标，再定方案”。延迟不是单一指标：

1. **TTFT（首 token 延迟）**：影响用户“响应感”。瓶颈在 Prefill 阶段和网络。优化手段：缩短 prompt、语义缓存、把检索和 Prefill 并行化（RAG 场景）。目标一般 < 500ms。
2. **TPOT（每个 token 生成时间）**：影响用户“等待感”。瓶颈在 Decoding 阶段的显存带宽。优化手段：GQA、KV Cache 量化、权重量化、模型蒸馏。每 token 20-50ms 是常见范围。

吞吐与成本的关系：GPU 是固定成本，摊薄成本靠提高吞吐。**Continuous Batching** 是关键——传统 static batching 要等 batch 中最慢的序列完成才释放资源，GPU 空转严重；Continuous Batching 每一步动态插入新请求、移除已完成请求，GPU 始终在处理有效 token，吞吐可提升数倍。

工程组件细节：
- **语义缓存**：用 embedding 相似度判断命中（阈值 0.9+），缓存 key 要包含用户/租户信息，配合 TTL 过期。命中率 20%-30% 时收益非常可观。
- **PD 分离**：Prefill 计算密集、Decode 带宽密集，分离后互不抢占，还能按各自瓶颈独立扩缩容。
- **弹性伸缩**：按队列深度和 GPU 利用率做 HPA，避免波峰击穿、波谷浪费。

坑点：不要盲目上量化，必须先跑评测集验证精度；语义缓存要处理知识更新后的过期问题；PD 分离在低并发场景反而增加通信开销，要按 QPS 评估是否值得。

**常见追问与回答：**

Q1：TTFT 和 TPOT 哪个更重要？
A：取决于场景。聊天场景 TTFT 影响“响应感”，需要 < 500ms；长文生成场景 TPOT 影响“等待感”，要匀速稳定。PD 分离和流式输出就是分别优化这两个指标的手段。

Q2：语义缓存如何设计才能不返回过期答案？
A：缓存 key 加入文档版本号或知识库版本，知识库变更时主动失效对应缓存；同时设置 TTL，配合分权限缓存（不同用户/租户不可互读）。

Q3：Continuous Batching 的代价是什么？
A：单个请求的最差延迟可能变长，因为 GPU 资源被动态共享；需要通过调度策略（如带优先级的队列）保证长尾延迟不超标。

**项目联系：**
在部署项目中可以做一组 A/B 实验：基线是 vLLM 默认配置，实验组依次开启 Continuous Batching、INT8 量化、语义缓存。用同一份压测脚本记录 TTFT、TPOT、吞吐（tokens/s）和 GPU 利用率。面试时直接说“我通过三项优化把吞吐从 X 提升到 Y”，配数据，比任何概念描述都有力。

**记忆关键词：**
TTFT、TPOT、Continuous Batching、语义缓存、PD 分离、弹性伸缩

### 题目 3：如果量化后模型理解能力下降怎么办？如何做精度补偿？

**来源依据：**
- [AgentGuide 面试案例（GitHub）](https://github.com/adongwanai/AgentGuide/blob/main/docs/04-interview/12-company-interview-cases.md) - 面经或社媒 - 需进一步验证

**可信度：**
中（面经中的高频追问，且为部署落地常见问题）

**考察点：**
量化原理、精度损失定位、GPTQ/AWQ/SmoothQuant、混合精度、QAT

**面试口头版回答：**
量化掉精度一般从四个方向补偿。第一，换量化方法：从简单的动态量化换成 GPTQ 或 AWQ，它们会利用权重或激活的统计信息做误差补偿，损失更小；第二，混合精度：不是所有层对量化同样敏感，用校准集逐层评估误差，把 norm 层、attention 的 K/V 投影层保留 FP16，其余层用 INT8；第三，量化感知训练 QAT：用少量数据做低精度继续微调，让模型适应量化噪声；第四，系统兜底：在 RAG 或 Agent 场景里，通过改善检索质量、prompt 结构来降低对模型自身能力的依赖。最后一定要做评测回归，按任务维度看指标，防止修好一个任务、搞坏另一个任务。

**深入理解版回答：**

量化误差为什么会导致能力下降？链条是：权重量化引入误差 → Q、K、V 投影结果产生偏移 → QK^T 点积对误差敏感，softmax 的非线性会放大微小偏差 → 注意力分布被扭曲 → 模型“关注错了”或“关注模糊了” → 多层叠加后误差累积，长上下文任务尤其明显。

工程上的补偿手段：

1. **量化算法层面（PTQ）**：
   - GPTQ：用 Hessian 矩阵做二阶误差补偿，逐层重建权重，目标是让权重量化误差最小。
   - AWQ：根据激活值幅度识别重要通道，对重要通道做缩放保护，无需反向传播，校准数据需求少。
   - SmoothQuant：把激活值中的离群点转移到权重侧，让激活值也能被量化，解决激活动态范围大的问题。

2. **混合精度保护敏感层**：norm 层（RMSNorm/LayerNorm）、embedding 层、attention 的 K/V 投影层通常对量化更敏感。用几百条代表性样本做逐层量化误差注入，度量输出 KL 散度或余弦相似度，把高敏感层保留 FP16。

3. **QAT（量化感知训练）**：在量化模拟的 forward 下做少量步数的继续训练，让权重适应低精度噪声。注意：学习率要小，步数不能多，防止灾难性遗忘。

4. **系统级兜底**：在 RAG 中加强上下文排序和引用控制；在 Agent 中加入“不确定时先检索再回答”的行为约束；生成侧适当降低 temperature，减少随机性。

最后，评测回归必须分任务，而不是只看一个总准确率。量化前后对比要涵盖业务指标 + 通用能力指标（如指令遵从、代码、推理），防止“整体没降，某个关键子任务崩了”。

**常见追问与回答：**

Q1：如何判断哪些层是敏感层？
A：用校准集逐层注入量化噪声，观察模型输出的 KL 散度或下游任务指标变化。变化大的层标记为敏感层，保留高精度。这个过程可以自动化脚本化。

Q2：GPTQ 和 AWQ 有什么区别？
A：GPTQ 是权重重建视角，用二阶 Hessian 做误差补偿；AWQ 是激活感知视角，根据激活值幅度保护重要通道。AWQ 不需要反向传播，校准数据少，速度快。

Q3：QAT 和 PTQ 怎么选？
A：优先试 PTQ（成本低），精度不达标再上 QAT。QAT 需要额外的训练数据和评测流程，适合精度敏感场景。

**项目联系：**
在部署 LoRA 微调后的模型时，用 AWQ 量化到 INT4。先跑一套业务评测，记录下降幅度；再把 norm 层和 lm_head 通过 excluded_modules 排除在量化外，重新评测。面试时可以说“我对比过量化前后分任务指标，发现长文本任务掉 3 个点，保护敏感层后恢复到 1 个点以内”，这就是工程落地能力。

**记忆关键词：**
量化误差、GPTQ、AWQ、SmoothQuant、QAT、敏感层保护

### 题目 4：如何估算 LLaMA-7B 模型推理时的显存占用？

**来源依据：**
- [AgentGuide 面试案例（GitHub）](https://github.com/adongwanai/AgentGuide/blob/main/docs/04-interview/12-company-interview-cases.md) - 面经或社媒 - 需进一步验证

**可信度：**
中（面经中出现的估算题，属于部署工程师的基本功）

**考察点：**
显存组成、权重/KV Cache/激活值估算、GQA 的影响、部署参数计算

**面试口头版回答：**
推理显存分三块算。第一块是权重：7B 参数用 FP16 就是 14GB，INT8 是 7GB，INT4 约 3.5GB。第二块是 KV Cache：公式是 2 × 层数 × KV 头数 × 头维度 × 精度字节 × 序列长度 × batch。LLaMA-2-7B 是 32 层、GQA 8 组、头维度 128，FP16 下每 token 约 128KB；2048 token 单序列约 256MB，batch 8 约 2GB。第三块是激活值和运行时开销：激活值与 hidden_size、seq_len 有关，一般预留 2-4GB。所以 7B FP16、2048 上下文、batch 8 大约需要 14 + 2 + 4 = 20GB 显存，A100-40G 或 4090 可以跑。

**深入理解版回答：**

显存估算公式是部署选型的基本功，要能拆开讲：

1. **权重显存**：`参数 × 每参数字节数`。FP16/BF16 是 2 字节，INT8 是 1 字节，INT4 约 0.5 字节。注意 INT4 还有少量 scale 参数，实际略高。

2. **KV Cache**：`2 × L × H_kv × D_head × 字节数 × seq_len × batch`。关键变量是 H_kv（KV 头数）。LLaMA-1-7B 没有 GQA，H_kv=32，每 token 512KB；LLaMA-2-7B 用了 GQA，H_kv=8，每 token 128KB，差 4 倍。这就是业界普遍转 GQA 的原因——不仅是训练效率，推理时 KV Cache 和带宽压力直接减少数倍。

3. **激活值**：最难估算的部分。它与 batch、seq_len、hidden_size、层数相关，粗略估计每层激活 ≈ batch × seq_len × hidden_size × 常数，叠加后通常几个 GB。更准确的方式是通过 PyTorch profiler 或 vLLM 日志实测。注意 Prefill 阶段由于并行处理整个 prompt，激活峰值远高于 Decoding 阶段，OOM 往往发生在 Prefill。

4. **部署预留**：vLLM 的 `gpu_memory_utilization` 参数（如 0.9）控制权重 + KV Cache 的目标占用率，剩余空间留给激活值和 CUDA context。实际部署还要算上框架运行时开销（几百 MB 到 1GB）。

常见坑：
- 只算权重不算 KV Cache（高并发长上下文时 KV 可能超过权重）；
- 不考虑 GQA，用全部 head 计算导致估值翻倍；
- 不区分 Prefill 和 Decoding 的激活峰值差异。

**常见追问与回答：**

Q1：为什么 7B 模型不能只看 14GB 权重？
A：因为 KV Cache 随并发数和序列长度线性增长，batch 8、2048 上下文时约 2GB；加上激活值和运行时，轻松超过 20GB。

Q2：batch 增大时显存增加主要在哪里？
A：KV Cache 和激活值都随 batch 线性增加，但权重不变。这就是为什么 batch 越大单位成本越低——权重是共享的。

Q3：如何验证估算是否准确？
A：用 vLLM 启动时日志中打印的 KV Cache 池大小，或 nvidia-smi 观察进程峰值显存，对比估算值，误差一般能控制在 10%-20% 内。

**项目联系：**
在部署选型阶段，可以用“显存计算器”脚本输出不同精度、并发、序列长度下的显存需求。比如在 4090（24GB）上用 INT8 部署 7B 模型：权重 7GB，单序列 2048 的 KV 约 256MB，理论上可支持 20+ 并发，再对比 vLLM 实际可跑的最大并发数。面试时能主动报出“估算 vs 实测”的对比数据，是很好的亮点。

**记忆关键词：**
权重显存、KV Cache 公式、GQA、激活值、gpu_memory_utilization

- **核心内容总结：**
  - 大厂面试流程一般为三到四轮：技术基础 + 项目深挖 → 业务场景 + 系统设计 → 综合素质/交叉面。

  - 手撕代码曾出现“手写 MHA（仅 numpy）”，说明 Attention 计算链路必须理解到能手动实现的程度。
  - 项目深挖的风格是连环追问：embedding 模型结构 → 输出维度 → chunk 模型 → 向量库构建，每个环节都会被继续追问。
  - Agent 方向必问：工具调用稳定性、memory 设计、死循环处理（迭代限制/循环检测/降级）。
- **对面试有什么用：**
  - 明确 KV Cache 相关题目出现的“位置”——通常是技术面或项目深挖阶段。
  - “手写 MHA”提示需要掌握 attention 的每个计算步骤，这正好是 KV Cache 优化的基础。
- **可转化面试题：**

  1. 手写 MHA 时，如果去掉 KV Cache 会有什么影响？

  2. 注意力机制为什么要除以根号 d_k？量化后这个数值假设还成立吗？

- **对应参考答案：**

  1. 去掉 KV Cache 后，Decoding 阶段每个新 token 都要重新计算历史所有 token 的 K/V，计算量从 O(n) 变为 O(n²)（按已生成长度计），生成速度显著下降。显存上虽然省了缓存，但激活值临时计算量增大，实际上得不偿失。所以生产推理框架只会优化 KV Cache 的存储，不会去掉它。

  2. 除以 sqrt(d_k) 是为了让 Q·K 点积的方差保持在 1 附近，防止 softmax 进入饱和区导致梯度消失或注意力过于尖锐。量化后权重噪声会让点积方差发生偏移，这是量化模型注意力“变模糊”的原因之一，也是 AWQ 等激活感知量化方法要做通道缩放补偿的原因所在。

## 3. 今日必背问答卡片

### 卡片 1

- **Q：** KV Cache 为什么能加速推理？它消耗的是什么资源？
- **A：** 自回归生成时，每个新 token 都要与之前所有 token 计算注意力。KV Cache 缓存已计算的 K/V 矩阵，避免每步重复计算，使 Decoding 计算量从 O(n²) 降到 O(n)。消耗的是显存，本质是“空间换时间”。
- **一句话记忆法：** 缓存 K/V，少算一遍；显存换速度，空间换时间。
- **复习标签：** #模型部署 #推理优化 #KV Cache

### 卡片 2

- **Q：** 如何估算模型推理时的显存占用？
- **A：** 总显存 = 权重 + KV Cache + 激活值 + 运行时开销。权重 = 参数量 × 字节数（FP16 为 2 字节）；KV Cache = 2 × 层数 × KV 头数 × 头维度 × 精度字节 × 序列长度 × batch。7B 模型 FP16 权重约 14GB；GQA 8 组下 KV Cache 约 128KB/token。
- **一句话记忆法：** 权重 + KV + 激活，三大件别漏算；7B 权重 14G，KV 随序列和并发翻倍。
- **复习标签：** #模型部署 #显存估算 #KV Cache

### 卡片 3

- **Q：** TTFT 和 TPOT 分别指什么？如何优化？
- **A：** TTFT 是首 token 延迟，优化靠缩短 Prefill、精简 prompt、语义缓存；TPOT 是每个生成 token 的时间，优化靠减少 Decoding 带宽需求，如 GQA、量化、蒸馏。两者的 SLO 要分别制定，不能混为一谈。
- **一句话记忆法：** TTFT 靠缓存快速响应，TPOT 靠压缩带宽走。
- **复习标签：** #模型部署 #延迟优化 #服务SLO

### 卡片 4

- **Q：** 量化后模型能力下降，有哪些补偿手段？
- **A：** 四板斧：一换更好的量化方法（GPTQ/AWQ/SmoothQuant）；二混合精度，敏感层（norm、K/V 投影）保留 FP16；三 QAT，用少量数据做量化感知微调；四系统兜底，在 RAG/Agent 中用检索和重写降低模型压力。最后用分任务评测集回归验证。
- **一句话记忆法：** 换方法、保敏感层、微调适应、系统兜底，四招补精度。
- **复习标签：** #模型部署 #量化 #精度补偿

### 卡片 5

- **Q：** Continuous Batching 为什么能提升吞吐？
- **A：** 传统 batching 要等 batch 中最慢的序列生成完才释放资源；Continuous Batching 在每一步解码后动态插入新序列、移除已完成序列，GPU 始终处理有效 token，吞吐显著提升，配合 PagedAttention 的显存管理可支持更大并发。
- **一句话记忆法：** 不等最慢的，先跑完的先进场，GPU 不闲更有吞吐。
- **复习标签：** #模型部署 #吞吐优化 #vLLM

## 4. 今日面试专项训练

### 4.1 大模型理论追问题

**问题：**
为什么 INT8/INT4 量化会导致模型能力下降？请从注意力机制的数值分布角度分析原因，并给出工程上的缓解手段。

（来源依据：AgentGuide 面试案例中的“如果量化后理解能力下降怎么办?怎么做精度补偿?”，属于原题的延伸理论追问，需进一步验证）

**面试口头版参考答案：**
量化的损失来自数值精度不足。注意力机制中，Q 和 K 的乘积会经过 softmax，softmax 对输入数值非常敏感，量化误差会让某个注意力的 logit 偏大或偏小，softmax 概率分布就扭曲了，模型会“看不清”该注意的位置。而且 K 的数值分布往往有离群值，直接均匀量化会放大误差。工程上常用 AWQ 这类激活感知量化，按通道缩放权重来保护重要特征；或者用 SmoothQuant 把激活中的离群值转移到权重上；还不够就用混合精度保护敏感层，或做 QAT 让模型适应量化噪声。

**深入理解版参考答案：**
量化误差的传播路径可以拆成三步：

第一步，权重 W 被量化后，Q、K、V 的投影结果产生误差。由于量化是均匀分段近似，对数值大的离群值（outlier）误差尤其大。

第二步，注意力分数 QK^T 是两路误差叠加，softmax 的指数运算会把误差非线性放大。比如原本 attention logit 是 [2.0, 1.0]，softmax 后是 [0.73, 0.27]；如果量化误差让 logit 变成 [1.6, 1.4]，softmax 变成 [0.55, 0.45]，注意力分布被“抹平”，模型无法聚焦关键 token。

第三步，多层叠加后误差累积。每一层的输出又成为下一层的输入，误差沿着层数放大，深度模型尤其明显。长上下文任务更严重，因为参与 attention 的 token 更多，误差叠加次数更多。

工程缓解手段：
- 量化算法层面：SmoothQuant 的核心是把激活值中的离群点通过数学等价变换转移到权重侧，降低激活的量化难度；AWQ 则根据激活幅度识别重要通道，只对重要通道做缩放保护，不需要反向传播。
- 敏感层保护：用校准集逐层度量量化误差（输出 KL 散度/余弦相似度），norm 层、K/V 投影层通常最敏感，保留 FP16。
- QAT：把量化噪声模拟进 forward，用直通估计（STE）反向传播，让权重学会适应低精度表示；学习率要小、步数要少，防止灾难性遗忘。
- 系统级兜底：在 RAG 中加强检索质量与上下文排序，让模型更“容易”地利用上下文；在 Agent 中加入“检测到不确定时优先查询再回答”的行为约束。

**2 个可能追问与简短回答：**

Q1：为什么 AWQ 能比 GPTQ 更关注激活值？
A：GPTQ 从权重重建角度做二阶误差补偿，假设所有权重的误差影响类似；AWQ 观察到不同通道对激活值变化的敏感性不同，通过校准集统计激活幅度，对重要通道做缩放保护。AWQ 不需要反向传播，校准数据更少。

Q2：如果量化后模型在长上下文任务上下降明显，你会优先排查哪里？
A：先检查 KV Cache 是否也被量化。很多框架权重 INT8 但 KV Cache 保持 FP16；如果 KV Cache 也量化了，长上下文下误差随序列长度累积会非常严重。第二个检查点是 RoPE 位置编码的计算精度，RoPE 的三角函数值在低精度下容易溢出或失真。
