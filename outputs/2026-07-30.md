### 题目 1：在 RAG 系统中，你如何设计一个系统的 Bad Case 分析流程？当发现模型输出与检索到的文档内容不一致时，你如何定位是检索失败还是生成失败？

**来源依据：**
- 大厂LLM应用岗上岸面经：面28家拿offer，拆解“必问考点+避坑指南” - https://juejin.cn/post/7531039727782068274 - 技术博客 - 需进一步验证

- 根据上述资料延伸，需进一步验证

**可信度：** 中（基于技术博客常见问题总结，无直接面经出处）

**考察点：** RAG 故障诊断；Bad Case 分类方法论；检索与生成解耦

**面试口头版回答：**  
我会设计一个三级归因的 Bad Case 分析流程。第一级，把 Bad Case 分为“答案错误”和“答案缺失”两大类。第二级，对于答案错误，检查检索到的文档是否包含正确信息：如果文档正确但生成错误，就是生成失败（幻觉）；如果文档本身错误或缺失，就是检索失败。第三级，对检索失败再细分为：query 改写后语义偏离、embedding 模型召回率不足、reranker 排序把正确文档排到后面等。实际工程中，我会把每条 Bad Case 都记录到表格中，包含 query、检索到的 top-k 文档、最终答案、以及标注人员标记的失败类型。每周周会上逐条复盘，优先修复出现频率最高的那类问题。

**深入理解版回答：**  
一个系统的 Bad Case 分析流程通常包括四个阶段：数据收集、失败分类、根因定位、方案验证。  

1. **数据收集**：线上日志中按一定比例采样（如 1%），或者由用户反馈、质检团队标注获取。每条 Bad Case 至少记录 query、retrieved chunks（带得分和原始文本）、final response、预期正确结果。  
2. **失败分类**：常见分类体系包括：  
   - 检索端：recall 不足（真正相关的 chunk 没被召回）、precision 不足（召回大量无关 chunk 混淆判断）、排序不当（相关 chunk 排在后面被截断）。  
   - 生成端：faithfulness 失败（生成内容与上下文矛盾）、relevance 失败（生成答非所问）、factuality 失败（生成事实错误的内部知识，而非使用上下文）。  
3. **根因定位**：例如，发现答案与检索文档不一致时，可人工判断：如果文档中明确包含正确答案但模型没采用，则为生成失败；如果检索文档不包含正确答案，则为检索失败。进一步，对于检索失败可检查 query 是否被 rewrite 改变了原意、embedding 模型维度是否足够区分相似内容、chunk 切分是否破坏了关键信息。  
4. **方案验证**：针对高频失败类型，设计 A/B 实验，验证改进后 Bad Case 的修复率。  

常见工程陷阱：只关注整体指标而不分析分类原因；Bad Case 标注成本高，可先用自动化的 LLM-as-Judge 粗略分类，再人工抽检。

**常见追问与回答：**  
- **追问1：如果检索到的 chunk 中同时包含正确答案和错误信息，模型用了错误信息，你认为是检索失败还是生成失败？**  
  答：这是生成失败（faithfulness failure），因为模型没有遵循“仅使用上下文信息”的指令。解决方案可以是加强 prompt 约束，或者使用后处理步骤（如答案与上下文字符串匹配检查）。  
- **追问2：你有遇到过因为 chunk 切分导致信息丢失的 Bad Case 吗？如何改进切分策略？**  
  答：遇到过，比如一个技术参数被切到两个 chunk 里，单个 chunk 不完整。改进方法：采用滑动窗口重叠切分（如 chunk 512 tokens，overlap 64），或者使用语义边界切分（如段落、句子）而非固定 token 数。

**项目联系：**  
在我的 RAG 项目中，我建立了一个 Bad Case 库，用阿里云的 Label Studio 做了标注平台，每周复盘。有一次发现 40% 的 Bad Case 属于“正确答案在排序 3-5 名里但没被送入生成器”，于是把 reranker 的 top-k 从 3 改到 5，效果提升了 12%。

**记忆关键词：**  
Bad Case 分级；检索 vs 生成归因；chunk 切分；faithfulness 检查

### 题目 2：你了解 LLM-as-Judge 这种评测方法吗？在 Agent 场景下使用它有什么局限性？如何缓解？

**来源依据：**
- Top Interview Questions on RAG for Data Science and AI Engineer Roles - https://buildml.substack.com/p/top-interview-questions-on-rag-for - 技术博客 - 需进一步验证
- GenAI & Agentic AI Interview Questions (2026) - https://agentswarms.fyi/interview-questions - 技术博客 - 需进一步验证
- 根据上述资料延伸，需进一步验证

**可信度：** 中（基于社区公认技术点，多家文章提及）

**考察点：** LLM-as-Judge；Agent 评测难点；偏差缓解

**面试口头版回答：**  
LLM-as-Judge 就是用一个大模型（比如 GPT-4）来评估另一个 LLM 的输出质量，通常给打分或判断好坏。在 Agent 场景下，它的主要局限包括：一是位置偏差——如果让 Judge 从多个输出中选择最好的，它倾向于选第一个或最后一个；二是自洽性偏差——Judge 模型自己的观点可能影响打分，比如它喜欢长回答；三是无法有效评估多步推理的正确性，它只能看到最终结果。缓解方法：使用多 Judge 投票（比如用 3 个不同模型打分取平均）；打乱候选答案顺序做多次评测；设计细粒度的打分标准（如分步骤打分）；或者优先用人肉标注作为黄金标准，LLM-as-Judge 只做辅助。

**深入理解版回答：**  
LLM-as-Judge 是目前工业界常用的自动评测方法，因为它成本低、速度快。但存在多个已被实验证实的偏差：  
1. **位置偏差（Position Bias）**：在 pairwise 对比时，Judge 模型往往偏好更早出现的回答。2018 年的研究就发现 LLM 在序列中会衰减对中间内容的关注。  
2. **自我强化偏差（Self-Enhancement Bias）**：Judge 模型更倾向于与自己训练数据风格相似的输出。  
3. **长度偏差（Verbosity Bias）**：Judge 认为更长的回答更好，哪怕内容冗余。  
4. **无法评估过程正确性**：Agent 可能有多个中间步骤，比如调用工具失败后重新尝试，最终结果虽然正确但过程低效，Judge 无法给出过程分。  

缓解方法：  
- **In-context calibration**：给 Judge 一些极端示例做校准。  
- **Multi-agent voting**：用多个 Judge 模型（如 GPT-4、Claude、Gemini）分别打分，取多数或中位数。  
- **Rubric-based evaluation**：设计详细评分标准（如正确性、完整性、效率），要求 Judge 分维度打分并给出理由。  
- **Human-in-the-loop**：对 Judge 结果分歧大的样本，人工介入。  

工程上，我会优先在 Agent 评测中使用“任务成功率”和“工具调用准确率”作为硬指标，LLM-as-Judge 只用于评估回答的自然度和安全性。

**常见追问与回答：**  
- **追问1：你在实际项目中使用过 LLM-as-Judge 吗？具体怎么做的？**  
  答：用过。我们评测客服 Agent，用 GPT-4 作为 Judge，要求它先输出“符合标准/不符合标准”，并给出理由。我们发现 GPT-4 经常因为与客服风格不同而误判，后来改用 Claude，并加入 few-shot 示例（包括好评和差评），提升了一致性。  
- **追问2：如何验证 LLM-as-Judge 的可靠性？**  
  答：可以用人工标注 200 条样本作为 ground truth，计算 Judge 与人的 agreement（Kappa 系数），如果低于 0.6 则需要调整 prompt 或换模型。我们当时人工标注了 500 条，kappa 达到 0.72 才上线。

**项目联系：**  
我设计了一个自动评测管道：先用规则引擎检测工具调用是否正确（如调用了错工具就算失败），再用 LLM-as-Judge 评估最终回答的有用性。对于规则与 Judge 结果矛盾的样本，自动标记为“需要人工复审”。

**记忆关键词：**  
LLM-as-Judge；位置偏差；长度偏差；多投票；Rubric 设计

### 题目 3：对于 AI Agent，你如何做离线评测？请列举你关注的核心指标和评测方法。

**来源依据：**
- GenAI & Agentic AI Interview Questions (2026) - https://agentswarms.fyi/interview-questions - 技术博客 - 需进一步验证
- 大厂LLM应用岗上岸面经：面28家拿offer，拆解“必问考点+避坑指南” - https://juejin.cn/post/7531039727782068274 - 技术博客 - 需进一步验证
- 根据上述资料延伸，需进一步验证

**可信度：** 中（多篇面经博客提及 Agent 评测，但无单一权威来源）

**考察点：** Agent 评测维度；任务成功率；工具调用；效率指标

**面试口头版回答：**  
我认为 Agent 离线评测需要至少两个维度：任务完成度和交互成本。任务完成度方面，我会定义每个任务场景的成功标准（比如“用户成功下单”），然后计算成功率（完成数/总测试数）。交互成本方面，我会统计平均工具调用次数、平均轮数、平均响应时间。另外，我会单独评测 Agent 的工具调用能力：工具选择准确率（调用了正确的工具）、参数填充准确率（工具参数正确）、错误恢复率（工具调用失败后能否自动重试或降级）。测试数据我会准备 100-200 个涵盖正常、边界、异常场景的 case，标注好每一步的黄金答案。

**深入理解版回答：**  
Agent 离线评测相比传统 LLM 评测更复杂，因为引入多步交互和外部工具。我通常从以下四个维度构建评测框架：  

1. **任务成功指标**：  
   - **任务的最终状态**：是否达成目标（如：通过率 = 成功完成的任务 / 总任务数量）。注意“成功”需要明确定义，避免模糊。  
   - **中间步骤正确性**：可以用步骤级评测，比如检查每一步是否做了预期的工具调用。  
2. **过程效率指标**：  
   - **工具调用次数**：越少说明效率越高（避免循环调用）。  
   - **对话轮数**：平均多少轮推理完成。  
   - **推理延迟**：首 token 延迟和总耗时。  
3. **鲁棒性指标**：  
   - **错误恢复率**：遇到工具调用失败时，Agent 是否自动重试、换工具或咨询用户，而不是直接崩溃。  
   - **幻觉率**：Agent 编造工具返回结果或捏造信息。  
4. **交互质量指标**：  
   - **用户意图理解准确性**：能否正确解析模糊或省略的 query。  
   - **回答友好度**：由人工或 LLM-Judge 评判。  

评测方法上，我建议构建“测试故事集”：为每个业务场景编写 3-5 条测试用例，包括正常路径、异常输入、边界条件。执行后，用工具记录所有日志，再做自动打分。推荐使用 LangSmith、Weights & Biases 等平台的 trace 功能辅助。

**常见追问与回答：**  
- **追问1：如果两个 Agent 任务成功率相同，但一个工具调用次数比另一个多，你更倾向于哪个？**  
  答：取决于业务目标。对于高可靠性场景（如金融交易），宁可多调用工具确认，也要保证正确。对于用户体验优先场景（如聊天机器人），工具调用次数多会让用户等待，影响体验，所以更倾向于少的。我会同时展示两个指标，由产品决策。  
- **追问2：你如何自动检测 Agent 是否陷入死循环？**  
  答：我可以在 Agent 循环中加入步骤计数器，超过阈值（如 10 步）就强制中断并输出“我无法完成”，同时记录为失败 case。

**项目联系：**  
我的 Agent 项目是一个文档问答助手（工具包括搜索、计算器、日历）。我离线构建了 150 个测试 case，成功率从最初的 62% 提升到 85%，通过分析失败 case 发现大部分是因为工具描述模糊导致调用错误，后来改进了工具描述。

**记忆关键词：**  
Agent 离线评测；任务成功率；工具调用准确率；步骤计数；死循环检测

### 题目 4：请介绍 RAG 系统的离线评测指标，重点说明 Faithfulness（忠实度）和 Context Precision（上下文精准率）的含义和计算方法。

**来源依据：**
- LLM Evaluation and RAG Interview Questions - https://www.linkedin.com/posts/subrat-swain-abb3a622_genai-llm-rag-activity-7485922136537141248-PSwm - 面经或社媒 - 需进一步验证
- Top Interview Questions on RAG for Data Science and AI Engineer Roles - https://buildml.substack.com/p/top-interview-questions-on-rag-for - 技术博客 - 需进一步验证

**可信度：** 中（LinkedIn 推文和 Substack 技术博客，非官方）

**考察点：** RAG eval 指标；Faithfulness；Context Precision；Ragas 衡量

**面试口头版回答：**  
Faithfulness 衡量生成的答案是否完全基于提供的上下文，没有添加或捏造信息。比如上下文说“苹果的 CEO 是库克”，答案说“苹果 CEO 是库克，他出生于 1960 年”——第二句没有上下文中，属于不忠实。Context Precision 则衡量检索到的文档中，有多少是真正与答案相关的。比如你检索了 5 个文档，只有 3 个对生成答案有用，那么 Context Precision 大约是 60%。这两个指标常用 Ragas 库计算：Faithfulness 通过将答案拆解成若干 claim，检查每个 claim 是否可被上下文支持；Context Precision 则计算相关文档排名位置的倒序得分。

**深入理解版回答：**  
RAG 系统评测需要区分检索端和生成端。这里重点讲两个生成端的关键指标：  

- **Faithfulness（忠实度）**：由 Ragas 度量。计算步骤：1) 将生成的 answer 用 LLM 拆分成多个原子声明（claims），如“公司营收增长 20%”、“主要来自北美市场”。2) 对每个 claim，使用上下文判断能否被支持（支持即 faithful，不支持即 hallucination）。3) Faithfulness = 支持的 claims 数 / 总 claims 数。工程上需要注意：claims 的粒度要合适，太粗容易漏查，太细可能因表述差异而误判。  

- **Context Precision（上下文精准率）**：衡量检索到的 chunks 中，排在前列的 chunks 是否真的对答案有用。公式通常利用了“相关文档在排序中的位置”加权（比如 Mean Average Precision 的变体）。如果相关文档集中在 top-k 前列，分数会更高；如果相关文档分散在末尾，分数降低。意义：高 Context Precision 意味着检索系统能精准定位最相关的信息给生成器，减少噪声。  

推荐使用开源库 Ragas（https://github.com/explodinggradients/ragas） 或 DeepEval 进行自动化计算。注意这些指标依赖 LLM 来拆分 claims 和判断支持关系，存在一定误差，需要人工抽样验证。

**常见追问与回答：**  
- **追问1：如果一个答案完全正确但使用了训练集中的知识，而不是检索到的文档，算 faithful 吗？**  
  答：不算，faithful 要求严格基于检索上下文。但这种情况可能说明系统依赖内部知识，容易产生幻觉风险。  
- **追问2：你有没有遇到过 Context Precision 高但 Faithfulness 低的情况？**  
  答：会。比如检索到正确文档，但模型忽略了其中部分关键信息，而自行填补了错误细节。这说明生成端有问题，需要优化 prompt 或微调。

**项目联系：**  
我在项目中使用 Ragas 对 RAG 系统进行持续评测。有一次发现 Faithfulness 从 0.85 降到 0.72，排查后发现是文档更新后 chunk 切分策略没变，导致关键事实被拆散。调整切分策略后回归到了 0.88。

**记忆关键词：**  
Faithfulness；Context Precision；Ragas；claim 拆分；检索与生成解耦

### 题目 5：如何离线评测一个 LoRA 微调模型的性能？你不仅要关注整体指标，还要关注什么？

**来源依据：**
- 大厂LLM应用岗上岸面经：面28家拿offer，拆解“必问考点+避坑指南” - https://juejin.cn/post/7531039727782068274 - 技术博客 - 需进一步验证
- 2026大厂大模型/Agent面试题 - https://gitcode.csdn.net/6a236d7b662f9a54cb7a2bf1.html - 面经或社媒 - 需进一步验证
- 根据上述资料延伸，需进一步验证

**可信度：** 低（无明确来源推演，基于常见微调评测讨论）

**考察点：** SFT/LoRA 评测；过拟合检测；分布外泛化

**面试口头版回答：**  
LoRA 微调后的评测不能只看整体 loss 或 BLEU 分数，我还会关注三方面：一是验证集上的生成质量，包括语法流畅度、指令遵循度（用 LLM-as-Judge 打分）；二是过拟合检测——比较训练集和验证集上的 loss 差距，如果验证集 loss 不再下降或反而上升，说明过拟合；三是分布外泛化能力，我会准备一些与训练数据分布不同的测试用例（比如新领域的 query），看模型是否能保持基础能力。此外，我还会做分类准确率（如果是分类任务）或对话成功率（如果是对话任务）等任务特定指标。

**深入理解版回答：**  
LoRA 微调评测应该分层设计：  

1. **基础能力评测**：微调后模型不应丢失基础能力。可以准备一组通用 benchmark 如 MMLU（多任务语言理解）、HellaSwag（常识推理），观察分数是否下降超过 5%。如果下降过大，说明微调导致灾难性遗忘。  
2. **下游任务评测**：根据微调的目标任务构建测试集。比如是问答微调，就计算 Exact Match、F1、ROUGE-L、以及人工/LLM 打分。注意测试集必须与训练集无关。  
3. **鲁棒性评测**：包括对 prompt 措辞变化的敏感度、对噪声输入的处理能力。例如，把测试 query 中的几个词替换成同义词，看模型回答是否稳定。  
4. **过拟合检测**：监控训练 loss 和验证 loss 曲线。当验证 loss 在某个 epoch 后上升，而训练 loss 继续下降，就是过拟合的信号。此外，可以做“训练样本 recall”测试：给模型一个训练集中的 query，看它是否完整背诵答案（过拟合模型会一字不差地复述）。  
5. **与 baseline 对比**：与未微调的基座模型对比，确保微调有正向收益。  

工程注意点：LoRA 的 rank 选择会影响模型容量；学习率过大会导致权重震荡而损害泛化。建议做 learning rate 扫描实验。

**常见追问与回答：**  
- **追问1：你如何构建 LoRA 微调任务的评测集？规模多大？**  
  答：我通常从原始数据中随机留出 10%-20% 作为评测集，并保证包含所有类别。如果数据量少（少于 1000 条），采用交叉验证。  
- **追问2：如果评测集上分数很高，但上线后效果差，可能是什么原因？**  
  答：可能评测集与线上分布不一致（eg. 评测集都是标准问法，线上有口语化表达）；或者评测时没有考虑对话历史；或者评测指标不够全面（只关注 BLEU 没关注安全性）。

**项目联系：**  
在我微调 Llama 2 做客服问答的项目中，我构建了 500 条测试集，同时保留了一个通用基准 MMLU-20 题。微调后 MMLU 没掉，但客服准确率升了 15%，信心比较足才部署上线。

LoRA 评测；过拟合检测；灾难性遗忘；分布外泛化

## 3. 今日必背问答卡片

### 卡片 1
- **Q：** 什么是 LLM-as-Judge 中的位置偏差（Position Bias）？如何缓解？  
- **A：** 位置偏差指 Judge 模型倾向于选择列表中顺序靠前的答案。缓解方法：打乱候选顺序进行多次评测后取平均；使用多个不同 Judge 投票；引入详细评分标准减少主观判断。  
- **一句话记忆法：** “Judge 像人一样有选择困难，靠前选项占便宜，多摇几次号再取平均。”  
- **复习标签：** #评测 #LLM-as-Judge

### 卡片 2
- **Q：** 在 RAG 评测中，Faithfulness 和 Context Precision 各衡量什么？  
- **A：** Faithfulness 衡量生成答案是否完全基于检索到的上下文（无捏造）。Context Precision 衡量检索到的文档中有多少被生成器实际使用，以及相关文档是否排在前面。  
- **一句话记忆法：** “Faithfulness 帮你防幻觉，Context Precision 看你找对了好几手资料。”  
- **复习标签：** #RAG #评测

### 卡片 3
- **Q：** Agent 离线评测的核心指标有哪些？  
- **A：** 任务成功率、工具调用准确率、平均工具调用次数、错误恢复率、对话轮次、推理延迟。  
- **一句话记忆法：** “Agent 评测四件事：成不成、准不准、快不快、掉坑能爬出来。”  
- **复习标签：** #Agent #评测

### 卡片 4
- **Q：** 如何定位 RAG 系统的 Bad Case 是检索端还是生成端的问题？  
- **A：** 先检查检索到的 top-k 文档是否包含正确答案。如果包含但答案错误，属于生成端失败（faithfulness 问题）；如果不包含，属于检索端失败（recall 或 ranking 问题）。  
- **一句话记忆法：** “查文档：有答案却答错 → 生成器背锅；没答案 → 检索器该罚。”  
- **复习标签：** #RAG #BadCase分析

### 卡片 5
- **Q：** LoRA 微调后如何检测是否过拟合？  
- **A：** 比较训练集和验证集的 loss 曲线：验证集 loss 不再下降或上升时说明过拟合。还可以测试模型是否对训练集问题高度复述（一字不差）。  
- **一句话记忆法：** “验证集 loss 不再降，模型开始背答案——过拟合。”  
- **复习标签：** #LoRA #微调 #评测

## 4. 今日面试专项训练

### 4.1 大模型理论追问题

**问题：** 在 RAG 系统中，如果 LLM-as-Judge 评测结果显示 Faithfulness 分数 0.85，但人工抽检发现 30% 的样本中存在微小事实错误（例如日期差一年），你认为这可能是什么原因造成的？如何改进评测方法？

**面试口头版参考答案：**  
首先，Faithfulness 0.85 说明在 claim 级别原子判断上，大部分 claim 被判定为被上下文支持。但人工抽检发现微小错误，说明 LLM-as-Judge 对“完全一致”的判断可能过于宽松。比如 Judge 认为“2025 年”和“2026 年”相近就不扣分，但人工认为必须精确。改进方法：一是在评测时增加时间约束的专门子维度，比如要求 Judge 对每个涉及数字的 claim 严格检查是否与上下文完全一致；二是把评测粒度从 claim 级改为更细的子句级，同时提供精确匹配的 few-shot 示例校准 Judge 行为。

**深入理解版参考答案：**  
这种情况通常由 LLM-as-Judge 的“宽容偏差”导致。Judge 模型在判断 claim 是否被支持时，倾向于语义等价而非字面等价。例如，上下文写“2026 年 7 月”，答案写“2026 年”，Judge 认为后者被前者支持，但人工认为缺失具体月份即信息不完备。根本原因在于评测 prompt 的粒度设计不合理。

改进方案：  
1. **细化评分标准**：在 Judge prompt 中要求“sentence-level 支持性检查”，明确要求对时间、数量、专有名词必须完全匹配。  
2. **引入验证集校准**：用人工标注的 100 条 high/low correspondence 样本作为 few-shot，让 Judge 学会严格模式。  
3. **使用多维度打分**：比如分开打分“事实正确性”、“完整性”、“忠实度”，各自独立计算。  
4. **人工兜底**：LLM-as-Judge 只作为初筛，对低分或可疑高分样本（如 Faithfulness 高但人工抽检错误多的区间）进行人工复审。  

工程上我建议在评测管道中加入一个“数字/日期严格匹配检测”的规则模块，对答案中的数字与上下文进行字符串匹配，若不一致则直接标记为 Faithfulness 失败，权重调高。

**可能追问与回答：**  
- **追问1：如果 Judge 和人工一致率只有 60%，你会怎么处理？**  
  答：说明当前 Judge 不可靠，需要重新设计评分 prompt 或换模型。同时可以退而求其次，以人工评测为主要标准，Judge 仅做辅助筛选。并分析不一致的类型，针对性地调整评测维度（比如专门加一个“精确性”维度）。  
- **追问2：你如何保证人工评测的质量和一致性？**  
  答：首先制定标注手册，定义好打分标准。然后让每个样本由至少两个人标注，计算 Cohen's Kappa 一致性，低于 0.7 的样本重新讨论或抛弃。标注人员可以先培训用 20 条测试题考核。
